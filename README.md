# FlowCost — визуальный планировщик процессов (prototype 0.5.4)

FlowCost — локально запускаемое приложение для описания процессов компании на BPMN-inspired холсте, планирования задач, трудозатрат и инструментов, расчёта внутренней себестоимости, повторного использования процессов и совместной работы команды.

## Обновления в 0.5.4 — email verification и одобрение аккаунтов

- **Email обязателен.** Регистрация не создаёт сессию: пользователь должен перейти по одноразовой ссылке подтверждения, действующей 24 часа.
- **Одобрение администратора.** Даже после подтверждения email новый аккаунт не сможет войти, пока администратор его не одобрит. Админская учётная запись настраивается через `backend/.env`; встроенных паролей по умолчанию нет. Если все три переменные администратора убрать, при следующем запуске админские права будут сняты.
- **Панель регистраций:** `/team/admin` (кнопка видна только администраторам). Можно просматривать неподтверждённые заявки, повторно отправлять письмо, исправлять email для старых аккаунтов без адреса, одобрять или отклонять регистрацию.
- **Письма:** SMTP настраивается через переменные `FLOWCOST_SMTP_*`. Проверочные токены хранятся в БД только в виде SHA-256-хэша; ссылки одноразовые и истекают через 24 часа.
- **Старые аккаунты:** при миграции они не считаются автоматически подтверждёнными или одобренными. Для аккаунта с email запросите письмо повторно; если у старого аккаунта email отсутствует, администратор может добавить адрес и отправить подтверждение.
- **Локальная разработка:** если SMTP не настроен и `FLOWCOST_DEV_EMAIL_LOG_LINKS=true`, ссылка подтверждения записывается в консоль backend. Этот режим предназначен только для локального тестирования. В production установите `FLOWCOST_DEV_EMAIL_LOG_LINKS=false` и настройте SMTP.
- **Проверки:** backend-тесты покрывают регистрацию, подтверждение email, блокировку до одобрения, административное одобрение и права admin-only.

### Первичная настройка email и администратора

1. Скопируйте `backend/.env.example` в `backend/.env`.
2. Задайте уникальные `FLOWCOST_ADMIN_USERNAME`, `FLOWCOST_ADMIN_EMAIL` и `FLOWCOST_ADMIN_PASSWORD`. Пароль администратора — минимум 12 символов; пример в `.env.example` обязательно замените.
3. Укажите реальные SMTP-параметры `FLOWCOST_SMTP_HOST`, `FLOWCOST_SMTP_PORT`, `FLOWCOST_SMTP_USERNAME`, `FLOWCOST_SMTP_PASSWORD`, `FLOWCOST_SMTP_FROM`. Для стандартного порта 587 оставьте `FLOWCOST_SMTP_STARTTLS=true`.
4. Установите `FLOWCOST_PUBLIC_URL` в URL frontend, который будет доступен пользователям. При локальном запуске используйте `http://localhost:5173`.
5. Перезапустите backend и войдите с реквизитами администратора из `.env`. Откройте **Регистрации** в боковой панели и одобряйте аккаунты после подтверждения email.

Если SMTP ещё не подключён для локальной проверки, можно временно оставить `FLOWCOST_DEV_EMAIL_LOG_LINKS=true`: ссылка появится в терминале backend. Не включайте это на публичном/боевом сервере, потому что ссылка является секретом подтверждения. Не добавляйте `backend/.env` в Git и не отправляйте его в архивах.

## Обновления в 0.5.3

- **Курсоры привязаны к холсту, а не к окну.** Клиент отправляет координаты в пространстве React Flow; каждый браузер переводит их в свои экранные координаты с учётом собственного масштаба и панорамирования. Поэтому курсор коллеги указывает на одну и ту же точку графа при разном zoom/pan.
- **Больше нет стартовых сценариев.** Новые аккаунты начинают с пустой библиотеки. При миграции удаляются старый `demo-landing` и только неизменённые автоматически созданные копии; другие пользовательские процессы сохраняются. Импортируемые демо-файлы также исключены из архива релиза.
- **Удаление процессов.** Владелец может удалить процесс из боковой библиотеки. Перед удалением приложение просит подтверждение; процессы других владельцев удалить нельзя. Открытые вкладки коллег получают уведомление и возвращаются в библиотеку.
- **Видимость при создании.** Для каждого процесса можно выбрать «Закрытый» (видит владелец и приглашённые) или «Видимый всем» (любой зарегистрированный пользователь может найти и открыть его для просмотра). Право редактирования выдаётся отдельно через приглашение.
- **Чистая модель экспорта и тестов.** Тесты экспорта больше не зависят от автоматически засеянного примера; геометрия курсора вынесена в `frontend/src/lib/cursorCoordinates.js` и покрыта отдельными тестами.
- **Проверки:** 14 backend unit-тестов, 5 frontend-тестов и интеграционный smoke-тест двух аккаунтов прошли. Полную production-сборку Vite нужно проверить локально, так как установка npm-зависимостей в используемой среде завершилась по тайм-ауту.

### Создание процесса и доступ

Нажмите «+» рядом с разделом «Процессы». В диалоге задайте название, описание, папку и видимость. Публичный процесс доступен всем зарегистрированным аккаунтам только для чтения, пока владелец не выдаст право на редактирование. В списке процессов владелец может удалить свою запись кнопкой корзины.

## Совместная работа и доступы в 0.5.2

- **Исправлены импорты React hooks.** `AuthScreen.jsx`, `ShareModal.jsx` и `ProjectSettingsModal.jsx` теперь импортируют используемые `useState`/`useEffect`; в частности, диалог общего доступа больше не ломается при открытии.
- **Один процесс — одна ссылка — одно общее состояние.** Процесс, созданный аккаунтом, остаётся личным, пока владелец не выдаст доступ. Владелец может пригласить пользователя через меню процесса, а участник может запросить доступ у владельца.
- **Нет незаметного перехода в другую копию.** Если прямой URL ведёт на процесс без доступа, приложение показывает отдельный экран и не заменяет его первым процессом из личного списка.
- **Коллеги онлайн:** страница `/team/online` показывает активные аккаунты, процессы, которые они сейчас редактируют, и кнопку открытия общей версии. Для закрытого процесса название скрывается; можно отправить владельцу запрос доступа. Владелец увидит входящие запросы и может выдать редактирование/просмотр или отклонить запрос.
- **Присутствие:** клиент отправляет heartbeat раз в 10 секунд; неактивные вкладки удаляются из списка после 45 секунд без heartbeat. Список обновляется каждые 5 секунд. Курсоры по-прежнему передаются через WebSocket комнаты процесса.
- **Историческое поведение (удалено в 0.5.3):** в 0.5.2 новые аккаунты получали `Моя копия: …`. Начиная с 0.5.3 новые аккаунты стартуют с пустой библиотекой, а неизменённые автоматические копии удаляются миграцией.
- **Проверки:** backend unit-тесты, интеграционный сценарий с двумя учётными записями (запрос/одобрение доступа, redaction закрытого процесса в списке онлайн, курсоры, перемещение, удаление, история и SQLite), frontend route/model tests.

### Как начать совместную работу

1. Владелец открывает нужный процесс и в меню выбирает **Совместная работа**, затем добавляет логин коллеги с правом редактирования или просмотра.
2. Либо коллега открывает `/team/online`, находит владельца и нажимает **Запросить доступ** рядом с закрытым процессом.
3. Владелец открывает `/team/online` и одобряет запрос. После этого коллега открывает одну и ту же ссылку `/processes/<id>` — оба аккаунта редактируют общий граф, общий журнал и видят курсоры друг друга.

В версиях до 0.5.3 регистрация создавала отдельные копии стартового примера, поэтому их истории были независимыми. Теперь новые аккаунты не получают демо-процесс. Для совместной работы используйте одну ссылку и общий `process_id`.

## Исправление совместной работы в 0.5.1

- **Исправлен сбой записи WebSocket-изменений:** после выделения SQLite-персистентности в отдельный модуль оставался вызов `now_iso()` без определения в этом модуле. Поэтому сокет мог аварийно закрываться именно после попытки переместить или удалить блок. Теперь время записи передаётся в хранилище явно; интеграционный тест проверяет, что перемещение и удаление проходят до подтверждения и рассылки второму участнику.
- **Видимый статус ошибок:** красный статус теперь имеет приоритет над состоянием `dirty`; сообщение об ошибке не маскируется оранжевым «Синхронизация…». При неожиданном исключении backend отправляет понятное сообщение до закрытия сокета.
- **Защита от зависшего ACK:** если изменение не подтверждено за 8 секунд, клиент переподключается и сверяет подтверждение операции с сохранённой версией, вместо бесконечного ожидания.
- **Курсоры:** серверная ретрансляция курсора между двумя отдельными учётками остаётся в интеграционном smoke-тесте. В 0.5.3 добавлен перевод экранных координат в пространство графа, чтобы курсор оставался привязанным к объекту при изменении zoom/pan.
- **Прямые URL:** добавлены тесты разбора URL для холста, журнала, сметы, настроек и зон ответственности.

## Исправление совместной работы в 0.5.0

- **Одинаковая модель сравнения:** базовый снимок и граф на холсте теперь нормализуются одинаково. Это убирает синтетические изменения из дефолтных грейдов и legacy-полей связей, из-за которых редактор мог оставаться в оранжевом статусе и постоянно считать процесс изменённым.
- **Канонический снимок после операции:** сервер отправляет подтверждённый снимок процесса как автору изменения, так и остальным участникам. Клиенты обновляют из него базовую версию после перемещения и удаления узлов; изменения не восстанавливаются только локальной реконструкцией операций.
- **Курсоры:** клиент передаёт координаты после успешного присоединения к комнате; сервер ретранслирует координаты участникам этой комнаты. В интеграционный smoke-тест добавлена проверка курсора между двумя отдельными учётными записями.
- **Прямые ссылки на представления:** `/processes/:id`, `/processes/:id/activity`, `/processes/:id/estimate`, `/processes/:id/settings`, `/processes/:id/responsibility`, `/team`, `/team/tools` и `/team/financial-goals`.
- **Модульная структура:** компоненты интерфейса, модель процесса, URL-роутинг, операции синхронизации, расчёт стоимости и экспорт разделены на отдельные файлы. См. `docs/ARCHITECTURE.md`.
- **Проверки:** backend unit-тесты и реальная WebSocket-проверка двух пользователей выполняются отдельно; есть тесты frontend-модели на нормализацию, перемещение, удаление узла и прямые URL.

## Исправление 0.4.1 — CORS и цикл повторной загрузки

- **CORS на ошибках авторизации:** CORS middleware теперь внешнее относительно middleware проверки сессии. Даже ранние ответы `401` (например, истёкший токен в `/api/auth/me`) получают корректные CORS-заголовки, и браузер показывает содержимое ошибки, а не маскирует её сообщением о CORS.
- **Остановлен цикл загрузки:** `loadProcess` больше не пересоздаётся при каждом обновлении команды и грейдов. Подключение WebSocket больше не зависит от массивов справочников. Ранее загрузка workspace обновляла команду/грейды, что меняло зависимости `loadProcess` → `loadWorkspace` → effect `/api/auth/me`; эффект повторял загрузку справочников и создавал новый WebSocket после каждого прохода.
- **Понятная ошибка сессии:** после ответа `401` по `/api/auth/me` недействительный токен очищается, а экран входа объясняет, что нужно войти снова.
- **Проверки:** добавлены автоматические проверки CORS-заголовков на `401` от `/api/auth/me`, на неверный логин/пароль и на preflight `OPTIONS`.

**Примечание:** один ответ `401` от `POST /api/auth/login` сам по себе не является CORS-ошибкой — это означает, что сочетание логина и пароля не совпало. Теперь браузер может прочитать серверное сообщение «Неверный логин или пароль».

## Что нового в 0.4

- **Роли, грейды и команда:** ставки хранятся только на уровне «роль + грейд», без личных ставок сотрудников. У каждой роли ровно один дефолтный грейд; первый становится дефолтом автоматически, его можно поменять. Миграция существующей SQLite-базы восстанавливает дефолт, если его не было. Нельзя удалить последний грейд роли, пока к ней привязаны сотрудники.
- **Финансовые цели:** справочник хранит название фонда, месячную цель, начальный баланс и валюту. В настройках процесса задаётся процент от базовой сметы за каждый календарный месяц проекта. Сумма отчисления добавляется сверх основной сметы.
- **Операционная синхронизация:** изменения в графе отправляются как ограниченные операции, а не как полная копия процесса. Сервер сохраняет операции и ревизии в SQLite, подтверждает `op_id`, обнаруживает пересекающиеся изменения и восстанавливает состояние после переподключения. Устаревшее редактирование удалённого узла становится конфликтом с приоритетом удаления.
- **Сетевые меры защиты:** токен отправляется первым WebSocket-сообщением, а не в URL; проверяется Origin, права редактирования, размер пакета, частота сообщений и актуальность сессии. Для локальной разработки список Origin задан через `FLOWCOST_ALLOWED_ORIGINS`.

## Что было в 0.3

- **Интерфейс:** метрики процесса встроены в topbar; действия собраны в меню-гамбургер; библиотеку процессов можно скрыть; смету можно открыть сбоку холста без экспорта; подсказки скрываются, а клавиши описаны в отдельном popup.
- **Папки и сортировка:** процессы можно распределять по папкам и сортировать по имени, папке или времени изменения.
- **Валидация:** неполные карточки показывают предупреждение о недостающих обязательных полях.
- **Задачи:** у каждой работы есть исполнитель, часы, цель, ожидаемый результат, теги и настраиваемые поля. Дополнительные поля могут иметь типы «текст», «число», «переключатель» или «мультисписок» и независимые флаги показа на карточке, при открытии и включения в Excel.
- **Чек-листы:** критерии готовности добавляются и удаляются по отдельным кнопкам.
- **Ставки:** единый каталог команды и грейдов; личных ставок сотрудников нет. Ставки хранятся только на уровне «роль + грейд», и ставка выбранного грейда является единственным источником ставки для конкретной задачи.
- **Инструменты:** каталог месячных лицензий; инструмент назначается этапу. Его стоимость распределяется по календарной длительности этапа: `месячная цена × календарные дни / 30,4375`.
- **Автосохранение и отмена:** изменения автоматически сохраняются с небольшой задержкой; `Ctrl/⌘+S` запускает сохранение вручную, `Ctrl/⌘+Z` отменяет последнее зарегистрированное действие. История отмены локальна для вкладки/сессии и сбрасывается при открытии другого процесса.
- **Представление ответственности:** отдельный view автоматически строит дорожки по ролям на основе задач этапов. Из дорожек можно редактировать задачу, цель, ожидаемый результат, исполнителя, часы и грейд; изменения синхронизируются с этапом на холсте.
- **Аккаунты и общий доступ:** регистрация и вход без подтверждения email; владелец может открыть доступ к процессу по логину другого зарегистрированного пользователя — на просмотр или редактирование.
- **Совместная работа:** отображаются присутствие участников и курсоры, а отдельные изменения графа передаются другим открытым сессиям в реальном времени.

## Основные возможности

- Узлы: старт, этап, решение, завершение, вложенный процесс, стикер, риск и группа.
- Входы/выходы отображаются на карточках. Синие пунктирные связи синхронизируют выход одного узла со входом другого и не изменяют расчёт стоимости. Серые связи определяют маршрут процесса.
- Риски, стикеры и рамки групп не влияют на стоимость. Для оценки работ по снижению риска добавьте отдельную задачу.
- В ветке решения сценарии считаются альтернативными; итоговая оценка использует самый дорогой маршрут. Общая часть после ветвления учитывается один раз. Настоящие параллельные AND-ветки в этой версии пока не реализованы.
- Сохранённый процесс можно вставить единым вложенным блоком или развернуть его узлы в текущий холст.
- Экспорт Excel содержит восемь листов: сводка, этапы и задачи, участники, связи, самый дорогой маршрут, инструменты, каталог грейдов и финансовые цели. Дополнительные поля попадают в Excel только при включённом флаге «В Excel».
- JSON экспортирует версионированный нейтральный формат `flowcost.process.v3` с графом, ресурсами и расчётом.

## Запуск локально

Требования: Python 3.11+ и Node.js 20+ (или совместимые современные версии).

### 1. Запустить backend

Windows PowerShell:

```powershell
cd backend
py -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

macOS/Linux:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Документация API: `http://127.0.0.1:8000/docs`.

### 2. Запустить frontend

Во втором терминале:

```bash
cd frontend
npm install
npm run dev
```

Откройте `http://localhost:5173` и зарегистрируйтесь с логином, email и паролем (не менее 8 символов). В локальном режиме без SMTP ссылка подтверждения появляется в консоли backend, если в `backend/.env` включён `FLOWCOST_DEV_EMAIL_LOG_LINKS=true`; после подтверждения администратор должен одобрить аккаунт. Для реальной отправки писем настройте SMTP по разделу выше. Для работы между разными компьютерами используйте один общий backend URL в `VITE_API_URL` и разрешите Origin frontend-сервера в `FLOWCOST_ALLOWED_ORIGINS`; не запускайте отдельный backend на каждом компьютере, если ожидаете общую синхронизацию. Если API запущен на другом адресе, создайте `frontend/.env`:

```env
VITE_API_URL=http://127.0.0.1:8000
```

WebSocket принимает подключения только с явно разрешённых Origin. Для запуска frontend с другого hostname/IP задайте переменную перед стартом backend, например: `FLOWCOST_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173,http://192.168.1.20:5173`. Не ставьте wildcard `*` для рабочего окружения.

SQLite создаётся автоматически в `backend/data/flowcost.sqlite3`.

## Первый запуск

1. Создайте первый процесс из кнопки «+» в боковой панели. Укажите, будет ли он закрытым или доступным всем зарегистрированным пользователям для просмотра.
2. В каталогах команды, грейдов и инструментов проверьте демонстрационные записи, если они сохранились от предыдущей версии, и замените их данными вашей компании.
3. Выберите этап и заполните цель, ожидаемый результат, входы/выходы, чек-лист и назначенные работы.
4. Для каждой работы выберите исполнителя и, при необходимости, грейд. Часы работы должны указываться на уровне каждой задачи.
5. В поле инструментов этапа выберите используемые лицензии и задайте календарную длительность, чтобы распределить месячную стоимость.
6. При ветвлении решения задайте подписи связям, например «Да — нужен новый дизайн» и «Нет — есть готовые макеты».
7. Откройте «Смета» рядом с холстом: она обновляется вместе с текущей моделью и не требует экспорта.
8. При совместной работе откройте «Доступ», введите логин коллеги и выберите право на просмотр или редактирование. Коллеге сначала нужно зарегистрироваться.

## Тесты

Unit-тесты backend проверяют в том числе CORS для `401` и preflight-запросов. Сначала из корня проекта установите тестовые зависимости, затем запускайте тесты:

```bash
python -m pip install -r backend/requirements-test.txt
cd backend
python -m unittest discover -s tests -v
cd ..
```

Интеграционная проверка настоящего WebSocket-соединения (allow-list Origin, вход двух подготовленных тестовых аккаунтов, подключение редакторов, presence, ACK, рассылка второму клиенту, повтор операции и сохранение в SQLite) использует `httpx` и `websockets`. Регистрация, подтверждение email и администраторское одобрение отдельно проверяются в `backend/tests/test_auth.py`:

```bash
python -m pip install -r backend/requirements-test.txt
python scripts/smoke_collaboration.py
```

Скрипт использует временную тестовую SQLite-базу и порт `8877`, запускает backend в отдельном процессе и удаляет тестовую базу после завершения. Запускайте только когда порт свободен.

## Модель стоимости

Стоимость труда задачи рассчитывается как `часы × ставка выбранного грейда роли`. Персональной ставки у участника нет; если в старом процессе нет `grade_id`, используется дефолтный грейд роли для совместимости и нормализации. Стоимость инструмента рассчитывается пропорционально календарной длительности этапа, на который он назначен. Итоговый бюджет маршрута выбирает наиболее дорогую альтернативу и не складывает взаимоисключающие ветки. Сводка также отдельно показывает сумму по всем этапам, включая альтернативы, как справочный показатель.

Это внутренняя себестоимость. В текущую формулу не включены маржа, налоги, управленческие накладные расходы, резерв и клиентская наценка. Валюты автоматически не конвертируются; при нескольких валютах интерфейс показывает предупреждение.

## Важные ограничения текущего прототипа

- **Операционная синхронизация — промежуточный этап, не CRDT.** Сервер хранит ревизии и подтверждения, сливает независимые изменения, предупреждает о конфликтующих путях; при одновременном изменении одного поля действует принцип «последняя принятая операция побеждает». Для действительно устойчивого совместного редактирования ниже описан переход на Yjs/CRDT.
- **Курсоры и присутствие** видны, пока обе сессии подключены к одному backend-процессу. Состояние курсора не хранится. Для двух компьютеров они должны обращаться к одному URL backend, одной SQLite-базе и одному экземпляру Uvicorn; два отдельных backend на `localhost` — это два разных пространства и синхронизироваться между собой не будут.
- **История отмены** находится в памяти текущей сессии и не является постоянной историей версий. После перезагрузки нельзя восстановить старые операции через `Ctrl/⌘+Z`.
- **Каталоги ресурсов и финансовые цели** пока общие для одного экземпляра приложения, а не отдельные для организаций. Все пользователи этого экземпляра видят общий справочник ресурсов. Перед применением в нескольких независимых компаниях нужно добавить `workspace_id` и проверить изоляцию всех сущностей.
- Ветка процесса трактуется как альтернатива (XOR). Параллельные обязательные AND-ветки, вероятностные сценарии и точный расчёт циклов/итераций пока не поддерживаются.
- **Оставшиеся ограничения:** восстановления пароля и workspace-изоляции пока нет; также необходимы rate limiting для публичных auth-endpoints и операционный мониторинг SMTP. Не публикуйте API напрямую в интернет без TLS/WSS, резервных копий, rate limiting и ограничения доступа к admin-аккаунту.
- Presence/курсор хранятся в памяти одного процесса. Запускайте ровно один Uvicorn worker; несколько worker или контейнеров потребуют общего pub/sub. SQLite WAL не предназначен для общей базы на сетевом диске. Подробности — `docs/COLLABORATION_MIGRATION.md`.
- Excel экспорт предназначен для планирования и передачи, а не как первичный источник данных. Основная модель хранится в SQLite/JSON.

## Buildn.ai

JSON экспорт является нейтральным форматом FlowCost. Совместимость с конкретной схемой импорта Buildn.ai не заявляется до получения примера файла/описания API или схемы данных. После подтверждения формата можно добавить отдельный адаптер, не меняя внутреннюю модель процесса.

## Синхронизация: текущий режим и переход

Протокол v0.5 использует WebSocket-операции, последовательные ревизии, идемпотентные подтверждения, журнал операций, канонические снимки после каждой принятой ревизии и REST fallback при потере соединения. Это надёжнее передачи целого JSON-снимка, но при двух одновременных изменениях одного поля конфликт не разрешается автоматически без потерь: сервер фиксирует конфликт, а последняя принятая операция побеждает. Канонический снимок используется для правильного применения перемещения и удаления узлов между браузерами. При этом это всё ещё не CRDT. Для следующего этапа см. `docs/COLLABORATION_MIGRATION.md`: рекомендуемый путь — React Flow + Yjs shared document + Awareness, серверная авторизация и постоянное хранение обновлений. Полностью переписывать UI не требуется.

## Структура проекта

Основная карта исходников и границы ответственности модулей находятся в `docs/ARCHITECTURE.md`. Окна вынесены в отдельные React-компоненты, бизнес-правила — в services/lib, REST-эндпоинты — в роутеры, а синхронизация и её интеграционный сценарий — в выделенные модули и тест. Ключевые файлы:

backend/app/services/collaboration.py        # graph operations and conflict paths
backend/app/services/collaboration_store.py  # transactional snapshots/revisions/event journal

frontend/src/App.jsx                          # editor composition/orchestration

frontend/src/lib/routes.js                    # direct process/view URLs
