# FlowCost 0.4 — план перехода к надёжной совместной работе

## Короткое решение

**Не переписывать весь FlowCost и не заменять React Flow.** В v0.4 приложение переходит от пересылки полного JSON-графа к операциям по стабильным ID, версии, подтверждениям и журналу. Это промежуточный протокол, который позволяет уже сейчас проверять командный сценарий. Следующий целевой вариант — отдельный слой документа Yjs/CRDT для графа, пока FastAPI остаётся владельцем бизнес-правил, калькуляции себестоимости, каталогов, прав, импорта и экспорта.

Официальный пример React Flow для совместной работы использует React Flow вместе с Yjs и `y-websocket`. Это сильная отправная точка: не нужно придумывать собственный алгоритм согласования одновременных правок массива узлов/связей. Yjs поддерживает распределённые изменения документа, а Awareness используется для эфемерных данных вроде курсоров и присутствия. Ссылки — в разделе «Источники».

## Что делает v0.4

1. Клиент рассчитывает diff между базовым состоянием и изменениями пользователя и отправляет пакет WebSocket-операций по ID узлов, связей, работ и пользовательских полей.
2. Сервер внутри транзакции SQLite применяет пакет и увеличивает ревизию процесса.
3. Сервер записывает операцию в `process_events`, сохраняет receipt по `op_id`, отмечает изменённые пути в `process_path_versions` и отправляет ACK с номером ревизии.
4. Повторно отправленный `op_id` подтверждается тем же результатом. Повторное использование того же ID для другого пакета отклоняется.
5. После переподключения клиент получает актуальный снимок, проверяет receipt незавершённого пакета и пытается сохранить локальные изменения поверх новой версии.
6. Независимые изменения разных полей могут быть объединены. Пересечения фиксируются в ACK; если два человека меняют одно и то же поле, последняя принятая операция побеждает — это **не CRDT**.
7. REST-сохранение снабжено `expected_revision`; устаревший полный снимок не должен молча перезаписать более новую версию.
8. Токен не передаётся в URL WebSocket: авторизация идёт первым сообщением. Проверяются Origin, право доступа, лимит payload, количество операций/сообщений и периодически валидируется сессия.

## Ограничения текущего этапа

- Менеджер WebSocket-комнат, presence и курсоры находятся в памяти процесса. Текущий сервер — **один Uvicorn worker и один backend instance**. `--workers 2+`, второй контейнер или балансировщик без общего pub/sub создаст отдельные комнаты и приведёт к неполным broadcast.
- На конфликтующем поле нет семантического слияния: сервер обнаруживает конфликт, журналирует его, но принимает более позднюю операцию.
- `Ctrl+Z` пока относится к локальной истории интерфейса. Это не серверный undo, не отмена одной конкретной операции коллеги и не история версий, на которую можно откатить весь процесс.
- SQLite WAL улучшает сосуществование читателей и писателя, но писатель всё равно один; WAL рассчитан на процессы на одной машине и не должен быть размещён на сетевой файловой системе.
- Коллекции ресурсов, финансовых целей и сотрудников пока общие на весь экземпляр, а не сегментированы по workspace/company.

## Целевая архитектура

### Frontend

- Оставить React Flow и существующие компоненты узлов/инспектора.
- Вынести совместную работу в изолированный `CollaborationProvider`, чтобы компоненты не отвечали за websocket/retry/rebase.
- Использовать один Yjs document на процесс (например, `Y.Doc`): `Y.Map` с узлами по стабильному ID; `Y.Map` или вложенные shared types для связей и свойств; работы/чек-листы/входы/выходы — коллекции по стабильным ID, не редактируемые массивы с позиционными индексами.
- Синхронизировать граф в React через адаптер, который преобразует shared document в массивы `nodes` / `edges` для React Flow. Для частых изменений не пересоздавать весь граф, если можно обновить только изменившиеся сущности.
- Установить undo manager на нужные shared types и ограничить scope локальным пользователем/редактором: действие Undo не должно отменять свежую работу коллеги.
- Использовать Yjs Awareness для курсора, выделения узла, текущего пользователя и presence. Awareness — эфемерные данные, они не должны попадать в историю процесса или смету.

### Backend и долговременное хранение

- FastAPI остаётся основным API для аутентификации, ACL, каталогов, финансовых расчётов, создания/копирования/удаления процессов, Excel/JSON и импорта/экспорта.
- Для Yjs sync можно использовать отдельный Node-сервис `y-websocket` (самый короткий путь, близкий к официальному React Flow примеру) или отдельный collaboration adapter. Не переносить бизнес-логику себестоимости в Node.
- Выдавать краткоживущий одноразовый collaboration ticket из FastAPI. Сервер синхронизации проверяет ticket и право `view`/`edit` на room/process до присоединения и при смене прав. Не использовать долгоживущий Bearer-токен в query string и не логировать credentials.
- Каждый процесс хранить как snapshot документа плюс журнал binary updates. Периодически собирать snapshot и обрезать старые обновления только после успешной фиксации snapshot. Для приложения небольшой команды возможно хранение в Postgres; не рассчитывать на неограниченный рост SQLite-журнала.
- Если используется более одного backend/collaboration instance, добавить Redis Pub/Sub или другой общий transport между экземплярами и общее durable storage. Не полагаться на локальные `dict` комнат.

### Почему не просто Socket.IO

Socket.IO полезен для rooms, acknowledgements, reconnection и fallbacks, но доставка события по умолчанию не равна гарантированной сохранности: транспорт требует application-level event IDs, ACKs, персистентности и восстановления пропущенных offsets, если сообщения нельзя терять. В v0.4 уже есть базовые ACK/receipts/revisions, но это всё ещё собственный протокол. Для сложного интерактивного редактирования графа Yjs/CRDT обычно предпочтительнее, чем постепенное наращивание самописной логики merge.

## Предлагаемые этапы внедрения

### Этап A — стабилизировать v0.4 (сейчас)

- Оставить единственный backend-процесс.
- Проверить два браузера с правом edit и один с правом view.
- Добавить автоматические integration tests на реальный WebSocket endpoint: ACL, auth, ACK, повтор `op_id`, конкурирующие правки, reconnect и конфликт удаления.
- Добавить явный индикатор «Есть конфликт» с перечнем полей/версий, вместо одного toast.
- Добавить резервное копирование SQLite-файла и простой тест восстановления из копии.

### Этап B — измерить реальные сценарии

- Измерить размеры графов (узлы, связи, пользовательские поля) и частоту операций.
- Проверить 2, 5 и 10 редакторов, частое перемещение узлов, одновременное редактирование одной задачи, перерыв сети на 10–30 секунд, обновление страницы при неподтверждённом пакете.
- Прогнать матрицу браузеров и сетевых случаев: пропущенная ревизия, повтор ACK, просроченная сессия, закрытие доступа во время работы.
- Сформулировать поведение удаления узла при параллельном редактировании и UX разрешения конфликтов.

### Этап C — Yjs proof of concept

- На отдельной ветке интегрировать Yjs document и Awareness с текущим React Flow editor.
- Сначала синхронизировать только добавление/удаление/перемещение узла и ребра, затем поля задачи и элементы списков.
- Поддержать одновременные изменения разных свойств и одного свойства, undo/redo и возврат после сетевого отключения.
- Сделать round-trip адаптер `FlowCost JSON ↔ Yjs document`, чтобы не потерять текущие JSON/Excel-экспорты и сохранённые процессы.
- Проверить, что вычисление сметы работает на обычном материализованном графе, независимо от механизма синхронизации.

### Этап D — durable storage и безопасность

- Реализовать auth gate на collaboration room и короткоживущие tickets.
- Внедрить snapshot + incremental update persistence, compaction и backup/restore тест.
- Перед запуском за пределами локальной машины включить HTTPS/WSS, Origin allowlist, rate limit для регистрации/login, централизованные логи без токенов, политику хранения аудита и регулярные security updates.
- Перенести данные в PostgreSQL, если требуется несколько серверных экземпляров, несколько организаций, активная команда или повышенная нагрузка; сделать миграцию и проверку восстановления прежде масштабирования.
- Добавить `workspace_id` к пользователям, процессам, команде, ролям/грейдам, инструментам и финансовым целям. Проверить, что каждая операция и экспорт выполняются в пределах workspace.

### Этап E — производственное использование

- Провести тест совместного редактирования с реальными процессами команды.
- Подготовить deploy-конфигурацию, миграции БД, бэкап, процедуру rollback и мониторинг соединений/ошибок синхронизации.
- Лишь после успешного параллельного испытания включить новый provider по умолчанию; старый v0.4 protocol оставить как временный fallback на период миграции, затем удалить.

## Минимальная проверка перед внутренним пилотом

- [ ] Запустить один backend worker и открыть один и тот же процесс в двух отдельных браузерах.
- [ ] Переименовать этап в браузере A — браузер B должен увидеть изменение без ручного обновления.
- [ ] Изменить в A часы задачи, а в B — описание этапа; обе независимые правки должны сохраниться.
- [ ] Одновременно изменить одно и то же поле: приложение должно показать конфликт или документированное поведение, а не молча перезатереть изменение без следа.
- [ ] Удалить узел в A, одновременно редактируя его в B; клиент должен восстановиться и не застрять в состоянии «syncing».
- [ ] Отключить сеть на 10 секунд, продолжить менять граф, включить сеть и убедиться, что состояние сверилось с сервером.
- [ ] Повторить отправку того же `op_id`; сервер не должен повторно применять пакет.
- [ ] Войти как пользователь с `view`: он видит обновления, но не может сохранить изменения.
- [ ] Отозвать доступ или истечь сессии; последующие записи должны отклоняться.
- [ ] Проверить, что недопустимый Origin, JSON > 64 KB и чрезмерно частые пакеты блокируются.
- [ ] Создать резервную копию БД и восстановить её в отдельное тестовое окружение.

## Рекомендации по развёртыванию сейчас

1. Запускать один FastAPI/Uvicorn worker. В dev используйте `uvicorn app.main:app --reload --host 127.0.0.1 --port 8000`.
2. Не публиковать приложение напрямую в открытый интернет. Для пилота использовать localhost, локальную сеть/VPN или reverse proxy с HTTPS/WSS и явным списком разрешённых Origin.
3. При использовании другого hostname задавать `FLOWCOST_ALLOWED_ORIGINS` как точный список frontend Origin, разделённый запятыми. Не использовать wildcard в рабочем окружении.
4. Регистрация сейчас открыта и не требует подтверждения email; ограничьте доступ сетевым периметром и используйте уникальные пароли. Перед широким доступом нужны invite/admin controls, throttling и recovery flow.
5. Делать копию `backend/data/flowcost.sqlite3` при остановленном процессе или согласованным SQLite backup API. Не копировать только один файл WAL-базы во время записи.
6. Не размещать SQLite WAL на сетевом диске и не запускать несколько workers против одной локальной SQLite базы.
