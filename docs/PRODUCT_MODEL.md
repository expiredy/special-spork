# FlowCost 0.4 — модель продукта

## Базовая сущность: процесс

Процесс — ориентированный граф. Узел может быть стартом, этапом, решением, завершением, вложенным процессом, стикером, риском или визуальной группой. Серые связи описывают переходы процесса, а синие пунктирные — передачу данных между выходом одного узла и входом другого.

Внутри этапа хранятся:

- описание этапа, календарная длительность;
- входные данные и ожидаемые выходы;
- критерии готовности в виде редактируемого списка;
- инструменты, месячные лицензии которых распределяются по календарной длительности этапа;
- набор конкретных работ/задач с одним исполнителем на задачу;
- цель и ожидаемый результат каждой задачи;
- часы, теги, выбранный грейд и настраиваемые поля;
- цвет, положение и сведения о неполноте карточки.

У дополнительного поля есть тип (`text`, `number`, `toggle`, `multilist`), возможные значения, сохранённое значение и три независимых настройки: отображение на карточке, отображение при открытии редактора, включение в Excel.

## Каталоги ресурсов и ставка

Каталог команды содержит имя участника, роль и активность, но не содержит ставку. Ставки хранятся только в каталоге «роль + грейд». У каждой роли ровно один дефолтный грейд; первый грейд становится дефолтным автоматически, выбранный дефолт можно поменять. При миграции приложения дефолты нормализуются. При назначении участника задача получает дефолтный грейд его роли, при этом пользователь может выбрать другой грейд той же роли.

Для работы:

`стоимость труда = часы × ставка выбранного грейда роли`

Для инструмента, назначенного этапу:

`стоимость инструмента этапа = месячная цена лицензии × календарные дни этапа / 30,4375`

Если один инструмент назначен нескольким этапам, каждый этап получает пропорциональную долю затрат. Сейчас не рассчитывается распределение лицензий по фактической загрузке пользователей или доле использования.

## Оценка маршрутов

Исходящие обычные связи из узла «Решение» рассматриваются как альтернативы (XOR). Для заголовочной сметы выбирается наиболее дорогой маршрут; общие шаги после альтернативных веток учитываются один раз. Параллельные обязательные действия требуют будущего типа шлюза AND, где стоимость обязательных веток суммируется, а календарное время считается отдельно.

Актуальные составляющие в расчёте: труд и назначенные инструменты. Маржа, резерв, налоги, накладные расходы, клиентская стоимость и валютная конвертация должны быть отдельным слоем и не должны молча включаться во внутреннюю себестоимость.

## Представление ответственности

Responsibility view строит дорожки по ролям из задач всех этапов. Это сгенерированное представление, не отдельный первичный источник данных: изменения задачи синхронизируются с исходным этапом. На дорожке можно редактировать текст задачи, цель, результат, исполнителя, часы и грейд. Полная BPMN-диаграмма с lane/participant сущностями и независимым управлением последовательностями пока не реализована.

## Совместная работа

В версии 0.4 действуют аккаунты, права `view` / `edit`, presence и broadcast курсоров. Graph diff превращается в атомарный пакет операций по стабильным ID. Сервер последовательно применяет пакет в транзакции SQLite, пишет ревизию и журнал, возвращает idempotent ACK для `op_id`, отслеживает пересечения изменяемых путей, восстанавливает пакет по receipt после переподключения и проверяет права на каждую запись. REST-сохранение содержит `expected_revision`, чтобы не перезаписывать новую версию слепым снимком.

Это **не полноценный CRDT**: независимые поля сливаются, но конфликтующие правки одного поля не имеют семантического merge; побеждает последняя принятая операция с предупреждением. Presence и broadcast живут в памяти одного Uvicorn-процесса. Следующая архитектура и план проверок описаны в `COLLABORATION_MIGRATION.md`.

## Данные и разделение пользователей

Аккаунты владеют процессами; процесс можно выдать другому зарегистрированному пользователю только на просмотр или редактирование. Сейчас каталог команды, инструментов и грейдов общий внутри одного развёрнутого экземпляра. Для реального многопользовательского SaaS нужна сущность организации/workspace, членство пользователя в workspace и изоляция каталогов/процессов по этому workspace.

## Экспорт

Нейтральный формат `flowcost.process.v3` содержит узлы, связи, папку, описания, команду, инструменты, грейды и сводку затрат. Excel содержит восемь листов: Summary, Stages, Team, Connections, Costliest route, Tools, Role Grades и Financial Goals. Дополнительные поля включаются в Excel только при `export_to_excel: true`.

Прямая совместимость с Buildn.ai не заявляется, пока не предоставлен проверяемый формат импорта. Для поддержки Buildn следует разработать отдельный adapter, который преобразует FlowCost graph к подтверждённой схеме импорта.

## Финансовые цели

Финансовая цель моделирует плановый фонд/резерв: целевой ежемесячный объём, начальный баланс, валюта и состояние активности. Процесс может включать процент отчислений по каждой цели. Для оценки маршрута `monthly_contribution = base_cost × rate_percent / 100`, а `total_contribution = monthly_contribution × duration_days / 30.4375`. Отчисление прибавляется к базовой смете. В каталоге сумма по всем процессам представляет нормализованный месячный эквивалент — текущая версия не распределяет отчисления по календарным месяцам конкретных процессов, потому что в модели пока нет утверждённого графика старта/финиша; это нужно добавить перед использованием в детальном cash-flow forecast.

## Рекомендуемый следующий этап

1. Изоляция ресурсов через workspaces/организации и права ролей.
2. CRDT-слой для совместного редактирования, постоянная история версий и восстановление; см. план миграции.
3. Резервное копирование, мониторинг и защита внутреннего развёртывания.
4. Полноценные BPMN-шлюзы XOR / AND / OR и поддержка lane как первичных сущностей при необходимости обмена с BPMN-инструментами.
5. Реальные ставки: начисленная зарплата, доступные продуктивные часы, праздники, налоги и overhead; затем отдельный слой клиентской сметы.
6. Импорт/экспорт Buildn.ai после подтверждения контракта данных.
7. Постоянная история версий процесса, сравнение смет до/после и фактические часы для анализа отклонений.
